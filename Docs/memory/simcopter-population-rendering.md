# SimCopter population rendering

*How SimCopter renders cars (headlight beams) and people, and the ground-agent placement gotcha in the remake*

Findings from dumping the `GEO/*.MAX` packs and the ground-population code on 2026-06-24. See [[simcopter-mesh-orientation-rules]] for the mesh format and [[simcopter-ghidra-workflow]] for the toolchain.

- **Car "headlights" are Maxis face type `11` (translucent) cards.** Every `AUTO*`/`CARPOLIC`/`CARAMBUL` object has a row of `ftype==11` quads at the **nose** (Unreal +X, all at `Y=0`, low `Z≈46` model units), marching forward well past the body (e.g. AUTO body ends ~X183 but the beam cards reach X375-485). The original draws face type 11 alpha-blended (same as the rotor disc), so these are the soft headlight beams. The remake's ground agent built vehicles with the single-section `BuildPaletteColoredSection` (no translucent split), so they rendered as **opaque grey/blue blocks** = the "opaque headlights" complaint. Fix shipped: build vehicles with `BuildPaletteColoredSections` routing ftype 11 into a discarded section (drops the beams) and add real `USpotLightComponent` headlights at the front corners (`SimCopterGroundAgent::ConfigureVehicleHeadlights`, toggle `bEnableVehicleHeadlights`).

- **People are NOT in the GEO packs.** Dumping all 143/144/113 object names across sim3d1/2/3 finds no person/cop/ped mesh (only `CARPOLIC`, a police car). SimCopter's crowds/rescue victims come from `X/privanim.df` and the flat `BMP/PEOPLE1.BMP` sprite. **Decoded + live-validated 2026-06-26 (see [[simcopter-live-memory-rip]] and `Docs/OriginalGameFileFormats.md` "Faithful Extraction Method"):** privanim.df is a big-endian IFF "Doug" container; near pedestrians are **3D low-poly flat-shaded vector figures** (per-person 4x4 transform @person+0x1d8 via `FUN_004704d1(node,xform,3)`; 16.16 fixed affine compose `FUN_00470650`; 3D scene-grid linking - NOT sprite sheets), with the **`PEOPLE1.BMP` sprite as far-LOD** (drawn only when person is within `DAT_0058dc26`; `FUN_004c6450` gate). **Container fully decoded + deterministic extractor `Tools/privanim_extract.py`:** section dir (`SPR# ARPP ANIP ARCP ARLU BODC`), 12-byte node dir at marker+2, **21 figures**, **75-76 clip inheritance tree** (root `"New "`, `Ne##<-parent`, base xyz floats), BODC/ARLU = 40-byte node-defs `[0x12,1][3 floats][idx][name][parent]`, ARCP/ARPP = 4-byte coord streams `[s8 x][s8 y][u8 z][u8 t]` (t steps 8). **CORRECTIONS to earlier guesses:** ARPP records are 8 bytes not 40 (the 40-byte blocks are clip-table entries); `0x4cf0b0`/`0x4cf3b0` are node type-stubs (`return 0`), NOT geometry leaves; real parse is `FUN_004cfed0`(BODC)/`FUN_004d18e0`(ANIP); `0x4d4800` is a pure-virtual stub. **STILL OPEN (needs live game running or draw-consumer disasm):** exact meaning of the 4-byte coord record (line endpoints vs strip verts vs joint samples), role of `t`, and model-space scale - i.e. the final geometry primitive before glTF emit. Faithful remake = 3D flat-shaded segment meshes from BODC + sprite LOD fallback. **glTF export works (`Tools/privanim_to_gltf.py`): ARCP records render as recognizable line-segment people.** Display rules: (1) `t=8k+4` is a segment index (also bounds the stream); (2) records pairing by same `t` are LINE endpoints - render as discrete LINES not LINE_STRIP (strip = the "disjointed web"); (3) `z` byte bit7 splits each stream into 2 parts (bit7=0: signed z ~0..47; bit7=1: 2nd part, mask the bit). Open: are the 2 z-groups separate figures/LODs or halves of one + their relative offset (currently each part normalized to own origin for viewing). The remake reproduced "a body with charm" procedurally: `FSimCopterPopulationBody::BuildPerson` stacks colored boxes (legs/torso/arms/head + police cap), faces +X, feet at local Z=0, drawn with `M_SimCopterLitVertexColor`. Used by both NPC pedestrians and the on-foot player. The old `PEOPLE1.BMP` sprite path stays in `FSimCopterPopulationSprite` as a fallback.

- **Road vs rail XBLD ids (cars were spawning on train tracks).** From the mesh-library mapping + GEO names, verified by parsing the `.sc2` XBLD layer: power lines = `0x0E..0x1C` (`WR14..WR28`), **surface roads = `0x1D..0x2B`** (`RD29..RD43`), **rails = `0x2C..0x3A`** (`RL44..RL58`). The traffic spawner's `IsOriginalTrafficRoadTile` had matched `0x2C..0x3E` = rails, so every car drove on the train tracks. Fixed to `0x1D..0x2B` plus the elevated/bridge road ids (`0x45..0x48`, `0x4D/0x4E`, `0x5A/0x5B`). `IsSurfaceRoadTile` = `0x1D..0x2B`. (cape wells has 1394 road tiles, 99.4% in one connected graph; `0x1D`/`0x1E` straight roads dominate.)

- **Road routing is now a clean graph walk, not the decompiled table** (per user request 2026-06-24 to overhaul cars). Every road tile is a graph node linked 4-directionally to neighbouring road tiles (built in `RebuildSpawnData`). `ChooseNextRouteNode` walks the graph: from the current node pick a connected neighbour, exclude the previous node (no U-turns) unless dead-end, prefer continuing straight (max dot of in/out direction) ~70% / turn ~30%. Agents track `RouteTargetNodeIndex`/`RoutePrevNodeIndex`; `AssignNextTarget` advances them. Because it only ever returns an *adjacent* graph node, agents can never leave the road network (the old code had a 16% "drive to a random distant node" branch that sent cars beelining off-road). The decompiled `FUN_004b5290`/`ChooseOriginalTrafficStep` table was removed (recover from git if revisiting). Validated by replaying the graph: 200 cars × 300 hops, 0 stuck, 73% straight. **Agent movement is now kinematic** (`MoveComponent` sweep = false) so cars never jam/stall against each other or building corners; the route graph keeps them on roads and `UpdateGroundSnap` fixes height.

- **Pedestrians belong on the road-tile sidewalks**, not the empty land beside roads. The spawner now builds pedestrian nodes from surface-road tiles (`0x1D..0x2B`) with a per-tile lateral offset (`GetRoadSidewalkWorldOffset`, ~0.34*TileSize toward the edge parallel to the road), so cars keep the centre line and pedestrians line the sidewalk. (Old `IsPedestrianCandidateTile` put them on adjacent non-road tiles.)

- **Population world scale = 0.25.** The city + its cars/helicopters render original meshes at 0.25x of real cm (400cm remake tile stands in for the 1600-unit original). Pedestrian and on-foot-player capsules/bodies were authored in real cm, so they were ~4x too tall. `ASimCopterGroundAgent`/`ASimCopterOnFootPawn` now multiply capsule size, body height, proxy, walk-bob and the on-foot camera boom by `PopulationWorldScale (0.25)`. Movement *speeds* and route-node positions are deliberately NOT scaled (cross-city travel rate is unchanged; only apparent size shrinks). Vehicle visual was already 0.25 via `VehicleModelScale`; its capsule is now scaled to match.

- **OPEN traffic issues (2026-06-24, see `Docs/TrafficSystemNotes.md`).** User reports cars/peds run
  ~2 tiles off the road meshes in ONE axis (perpendicular axis is on-road), over buildings. City and
  traffic world formulas are *identical* (`WorldX=(FileX+0.5)*Tile-Half`, `WorldY=-(...)`, Tile=400,
  Half=25600), so it is a runtime mismatch, NOT a formula bug. Leading cause: `ASimCopterTrafficSystemActor::CityFile`
  defaults to `cape wells.sc2` but `ASimCity2000CityActor::CityFile` has no default and is set in
  `Content/CityRender.umap` - if they differ, road layouts differ. Also check the city actor's umap
  transform (a 90° yaw would give the one-axis symptom). **Robust fix:** make the traffic actor find
  the city actor (`GetActorOfClass`) and use ITS city path + TileSize + terrain params + `GetActorTransform()`
  for node positions. Other open items: power-line/rail-over-road crossing tiles (not in `0x1D..0x2B`,
  candidates `0x43`/`0x44`) split the graph and render no sidewalk; diagonal/curve roads need shape-aware
  waypoints (currently centre-nodes → square turns); user wants right-side lane offsets. NOTE: was
  blocked from grepping the umap for `.sc2`/transform strings (tool use rejected) - verify the umap's
  city `CityFile` + transform first next session.

- **Ground-agent placement gotcha (cars/peds hovering).** Agents are placed by snapping to the city collision. The old `UpdateGroundSnap` traced `ECC_Visibility` from only `+120cm`; that missed whenever the traffic spawner's estimated terrain Z (`GetTerrainTileCenterZ`, default `TileSize 400`, scale 200) differed from the city actor's actually-rendered surface, leaving everything in the air (and "not driving on the road"). The on-foot player never floated because it already traced from `+2000`. Fix: trace from `+GroundProbeUpCm` (2500) down `+GroundProbeDistanceCm` (4000) and snap on spawn (`SnapToGroundImmediate`). **Trace on `ECC_Camera`, not Visibility**: the city terrain/`OriginalMeshComponent` block all channels incl. Camera, while every agent/player capsule sets Camera→Ignore, so ground probes pass through other agents instead of stacking on them. Terrain collision is on by default (`ASimCity2000CityActor::bEnableTerrainCollision`).
